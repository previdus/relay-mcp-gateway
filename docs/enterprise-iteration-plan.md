# Enterprise review plan

Start from the customer: “Can I prove which identity can call which tool, which credentials can reach which destination, and what happens when a dependency fails?” Success requires enforceable boundaries, usable configuration, and measured evidence rather than a count of plugins.

The first twenty review scenarios each use customer, product, principal-engineering, developer, security, test and performance perspectives. Follow-up reviews are appended with evidence. A review is an evidence-based design pass, not a claim of complete feature delivery. Each result links to code/tests or identifies an explicit open limitation. These reviews do not replace the remaining article/paper programme.

| Iteration | Customer requirement / question | Engineering and test gate |
|---|---|---|

| 2 | Credentials must not cross an HTTP redirect | Real redirect receiver sees zero requests |
| 3 | Same hostname does not mean the same service | Port/scheme/path binding and negative tests |
| 4 | A legacy SSE server must not nominate an unrelated message endpoint | Explicit request-path allowlist and endpoint-event test |
| 5 | OAuth client secrets must only reach the designated identity service | Distinct OAuth-token binding purpose |
| 6 | Binding policy changes must fail closed when malformed | Strict parse/limits and error redaction |
| 7 | Configuration edits must not weaken deployment policy | Bindings owned outside editable database configuration |
| 8 | Cloud secret backends should be replaceable | Small credential-binding interface, no arbitrary module loading |
| 9 | Authentication credentials must not become backend credentials | Existing exchange/passthrough regressions and explicit trust contract |
| 10 | A routing plugin must not substitute another registered server/tool for the caller's authorized target | Core binds physical names and aliases to enabled admin-configured targets; adversarial same-tenant tests |
| 11 | A plugin must not accidentally leak inbound tokens | Inspect actual routing and inspection context surfaces |
| 12 | Can we safely run third-party plugins? | Explicit in-process trust boundary; isolate untrusted code externally |
| 13 | Azure, AWS, GCP, OCI and on-prem must have deployment choices | Portable topology and provider-specific identity/network responsibility map |
| 14 | Private endpoints and cloud metadata must be distinguished | Network egress policy and DNS-rebinding limitations explicitly documented |
| 15 | Key rotation must not require copying secrets into configuration | Reference-based configuration; restart/rotation semantics documented |
| 16 | Authorization dependency outages must not grant access | Real OpenFGA/PG failure and revocation checks |
| 17 | More replicas must not multiply quotas | Real shared-budget tests and local-only state disclosure |
| 18 | Credential checks must not add a network call per request | Parse/index policy once per load; no extra remote lookup in binding check |
