# Performance validation

The repository includes a bounded, repeatable end-to-end smoke benchmark. It drives MCP 2026-07-28 Streamable HTTP clients through the gateway to a local MCP upstream and reports calls per second, approximate p50/p95/p99 tool-call latency, event-loop delay, and process RSS/heap deltas. The latency histogram uses fixed 1 ms buckets, keeping the measurement memory bounded as request volume grows.

The benchmark explicitly enables `discoveryCacheTtlMs` on its homogeneous local upstream. Production defaults leave this off. When enabled, the gateway uses the official MCP v2 client's `connect({ prior })` support to skip the repeated modern `server/discover` round trip. The cache is short-lived, bounded, and keyed by the upstream, config revision, authenticated principal, declared callback capabilities, and a digest of actual upstream headers; custom transport plugins and SSE do not use it. Enable it only when all upstream replicas consistently support the same protocol era, and use a TTL appropriate to your deployment. The SDK makes cache freshness the host's responsibility and recommends keeping a cached result within one authorization context ([official v2 migration guide](https://github.com/modelcontextprotocol/typescript-sdk/blob/main/docs/migration/upgrade-to-v2.md)); this is why the feature is opt-in.

Run `npm run perf:smoke`. Defaults are 8 concurrent client sessions, a 2 second warmup, a 10 second measurement interval, a 15-second protocol discovery cache, and one physical target. Configure `RELAY_PERF_CONCURRENCY` (1–64), `RELAY_PERF_WARMUP_SECONDS` (0–60), `RELAY_PERF_DURATION_SECONDS` (1–180), `RELAY_PERF_DISCOVERY_CACHE_TTL_MS` (0 disables the cache; maximum 60 seconds), and `RELAY_PERF_ALIAS_TARGETS` (1–32). Output includes the upstream MCP method counts, which expose extra round trips such as per-call `tools/list` schema validation. Optional `RELAY_PERF_MAX_P95_MS` and `RELAY_PERF_MIN_RPS` make the script exit unsuccessfully when a locally chosen threshold is missed. These thresholds are machine-specific and should not be copied into production SLOs without workload and environment validation.

The benchmark creates both gateway and upstream in the same Node process and uses loopback HTTP. It intentionally reports a **local single-process smoke baseline**, not a capacity promise or a multi-replica/cloud/production SLO. It does not model authentication providers, policy databases, TLS termination, realistic payload distributions, long-lived streams, or network latency. A production performance program still needs representative data, independent load generation, database and policy backends, multi-replica testing, failure injection, and a soak interval. MCP’s stateless request model is designed to work with ordinary horizontally scalable infrastructure, but deployment behavior and shared state still need to be measured in the target environment ([MCP 2026-07-28 transport guidance](https://blog.modelcontextprotocol.io/posts/2026-07-28/)).

The smoke accepts `RELAY_PERF_ALIAS_TARGETS` (1–32). Values above one create a priority-routed public alias over identical local tool definitions and separate upstream servers. `RELAY_PERF_UPSTREAM_TTL_MS` controls the synthetic upstream's explicit MCP freshness hint; zero is the default. `RELAY_PERF_CONTRACT_CACHE_MAX_TTL_MS` controls the gateway's local cap and accepts zero to disable reuse. Output records each backend's MCP method counts and checks that the selected target is validated and exactly one tool call executes, while list lookups stay within the strict or cached bounds.

The event-loop metric is included because synchronous CPU work can delay unrelated request processing; Node’s guidance explains the relationship to throughput and denial-of-service exposure ([Don’t Block the Event Loop](https://nodejs.org/en/learn/asynchronous-work/dont-block-the-event-loop)).

## Current workspace measurements — 18 October 2026

Three repeated 8-session runs against the current workspace source completed 1,128/1,128 (112.42 calls/s, p95 84 ms), 1,024/1,024 (102.14 calls/s, p95 96 ms), and 1,021/1,021 (101.76 calls/s, p95 96 ms under CPU profiling). The one-session run reached 86.13 calls/s with p95 16 ms; the 16-session run reached 97.35 calls/s with p95 197 ms. All had zero call failures. Observed RSS deltas ranged from about 73 to 106 MiB in the plain runs; heap-used deltas ranged from about 71 to 100 MiB. A short V8 CPU profile sampled garbage collection heavily alongside transport writes and SDK error construction. This is enough to justify an allocation/lifecycle investigation, but not to identify a causal code regression.

These current runs are materially below the earlier 18 October record above (261.57 calls/s, p95 39 ms). That earlier measurement and these reruns used this local single-process smoke script, but the available workspace has no Git history to establish a source commit comparison and the environment could not provide an OS resource snapshot. Do not treat either number as a production capacity claim or infer a source regression from the comparison alone. The next performance review should profile request/response lifecycle allocations, explain SDK error construction, and benchmark any session-reuse change with identity/callback isolation tests before adoption.

The benchmark now reports upstream method counts for the measured interval and allows `RELAY_PERF_DISCOVERY_CACHE_TTL_MS=0` to disable discovery caching. On a same-session pair of default 8-concurrency runs, 15-second caching completed 1,010 calls (100.83 calls/s, p95 102 ms) with exactly 1,010 `tools/list` and 1,010 `tools/call` requests and no repeated `server/discover`. With caching disabled it completed 822 calls (81.75 calls/s, p95 121 ms), with 822 requests for each of `server/discover`, `tools/list`, and `tools/call`. Counters exclude warmup. This suggests about 23% throughput improvement from avoiding one protocol-discovery round trip in this local test; the live per-call schema lookup remains enabled. The short comparison is diagnostic, not a stable capacity guarantee.

## Alias contract-check cost — 18 October 2026

The new alias-pool smoke was run with four client sessions, a one-second warmup, and a three-second measurement. The one-target physical-path baseline completed 632/632 calls (210.21 calls/s, p95 27 ms). A two-target alias completed 338/338 calls (112.07 calls/s, p95 56 ms); a four-target alias completed 224/224 calls (72.25 calls/s, p95 137 ms). In strict mode, each success caused one `tools/list` against each configured target and one actual `tools/call` on the selected priority target, with zero failures. These are single short runs in one local process, and the one-target baseline does not include alias routing. They show that live cross-target verification has a meaningful local cost, but do not establish target-cloud latency or capacity.

The cache optimization was then compared on a two-target alias with four client sessions, one second warmup and five seconds measured. With an upstream `tools/list` TTL of 30 seconds and the gateway's default five-second cap, the run completed 443 calls (88.19 calls/s, p95 61 ms); the secondary backend was listed twice during measurement as the capped entry expired. With upstream TTL zero, it completed 312 calls (61.64 calls/s, p95 80 ms), with one secondary `tools/list` per call. Both runs had zero failures and one actual tool invocation per success. This paired local result suggests the standards-based bounded cache reduces overhead; it is one short run pair and does not establish stable capacity or production latency.

A subsequent default run passed the new method-count assertions at 1,021 calls (101.77 calls/s, p95 92 ms): each measured success had one schema lookup and one tool invocation, while no `server/discover` occurred during the measured window. A separate five-second cache-off verification passed at 424 calls (84.08 calls/s, p95 118 ms), with exactly one `server/discover`, `tools/list`, and `tools/call` per success.

The optimization improved throughput by about 3× and reduced p95 by 67–69% in this before/after loopback comparison, with zero failed calls. It has not solved performance validation: throughput flattens between 8 and 16 sessions, and the short-run memory deltas at concurrency 8 and 16 remain high.

On 18 October, the final current-source approval-gate build passed a 10-second, 8-session smoke through the default path with approval policy disabled: 261.57 calls/s, p50 30 ms, p95 39 ms, p99 47 ms, event-loop p99 16.71 ms, RSS +172.8 MiB, heap-used -11.9 MiB, and zero failed calls. This is consistent with the earlier 8-session baseline for throughput/p95 and shows no obvious default-path latency regression. It does not measure approval-required traffic: each approved action adds remote request and consume calls plus human wait time, and those dependencies need a separately representative benchmark. The short run also retains the RSS concern and is not capacity evidence.

A 60-second, 8-session run then completed 9,177 calls at 152.89 calls/s, with p50 41 ms, p95 113 ms, p99 149 ms, and zero failures. Event-loop delay reached 116.72 ms at its maximum. RSS rose by 219.3 MiB while heap-used rose by 8.1 MiB between the start and end snapshots. The much smaller end heap delta is consistent with garbage collection reclaiming transient heap, but a single before/after heap sample cannot prove absence of leaks; RSS growth, sustained p95, and event-loop spikes remain open. This 60-second check is a short soak, not a production soak qualification.

The upstream MCP client and transport are still created per operation. We reviewed reuse against the official v2 client lifecycle: `connect()` performs initialization, `close()` rejects all in-flight requests, and a legacy Streamable HTTP session pins a client to its transport. Although the 2026-07-28 era is stateless per request, reusing one client would still require strict identity/credential partitioning, per-call trace context, cancellation-safe leases, protocol-era transition handling, bounded expiry, and shutdown cleanup. Current local evidence does not justify introducing those risks; revisit only after profiling isolates handshake setup as the bottleneck and a prototype shows a meaningful gain. Sources: [SDK connect and close lifecycle](https://github.com/modelcontextprotocol/typescript-sdk/blob/main/docs/clients/connect.md), [protocol-era behavior](https://github.com/modelcontextprotocol/typescript-sdk/blob/main/docs/protocol-versions.md), and [legacy session scaling](https://github.com/modelcontextprotocol/typescript-sdk/blob/main/docs/serving/sessions-state-scaling.md).

A fresh 10-second default run on 18 October completed 1,054/1,054 calls (105.01 calls/s, p50 76 ms, p95 91 ms, p99 104 ms) with about 52 MiB RSS and 35 MiB heap-used growth between start and end samples. Every successful call issued exactly one `tools/list` and one `tools/call`; no discovery request occurred during measurement. The immediately following 10-second cache-off run completed 818/818 calls (81.46 calls/s, p50 98 ms, p95 118 ms, p99 128 ms) with about 96 MiB RSS and 76 MiB heap-used growth. It recorded one `server/discover`, one `tools/list`, and one `tools/call` for every success. This paired local smoke again suggests the opt-in discovery cache avoids a costly round trip; memory deltas and two short runs remain noisy diagnostics, not a production capacity claim.
