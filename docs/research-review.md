# Engineering literature review — 17 October 2026

Reviewed corpus: **20 engineering articles and 10 research papers**, linked below. Primary author/vendor publications were selected for direct relevance to tool mediation, permissions, evaluation, isolation and operations. This is a targeted engineering review, not a systematic literature review or an independent reproduction of published experiments.

Review scope: substantive article body sections and paper methods/design, evaluation and limitations relevant to the gateway were examined from full-text sources. This does **not** mean every appendix, proof, example or line of every source was read. No paper is counted from an abstract alone. The Saltzer–Schroeder paper was reviewed through its author-hosted Basic Principles and Descriptor-Based Protection sections; the index alone was insufficient. Paper versions below are pinned; later revisions may differ. Engineering articles are not counted as research papers, including the AWS article distributed as a PDF. Research files stay outside the distributed product; this report contains original summaries, not copied source texts.

The implementation choices are our engineering inferences from the sources. Vendor examples, historical vulnerability demonstrations and benchmark scores are not evidence of this gateway's performance or of current competitor defects. The separate [implementation plan](research-implementation-plan.md) was written before application changes.

## Findings that change this gateway

* Tool-name authorization leaves an important gap: the same tool may be safe for one recipient, amount or account and unsafe for another. Add deterministic argument restrictions, independent of the model and layered with existing permissions.
* Discovery is an exposure boundary. Existing drift pins help after review; optional mandatory enrollment closes the unpinned-new-tool gap. Pins establish metadata stability, not trustworthy behavior or signed code provenance.
* Human-readable metadata can conceal instructions with display controls. Optional rejection is a narrow, testable safeguard; ordinary text can still contain prompt injections.
* Security-denial tests must be paired with legitimate-action tests and actual upstream state checks. A system that denies every action is not useful; an emulator's claimed outcome is not execution evidence.
* Full information-flow defenses require trusted agent-runtime support. A stateless gateway cannot reliably infer data provenance from ordinary JSON arguments.
* Efficiency ideas such as tool search and code mode are promising but need a separate sandbox and measured benefit. Avoid adding unrestricted execution to the gateway process.
* A timeout does not establish failure of a side effect. Keep automatic retries disabled until an upstream idempotency contract supports them.

## Engineering articles (20)

| ID / primary source | Finding, limitation and gateway decision |
|---|---|
| A01 — [Writing effective tools for agents](https://www.anthropic.com/engineering/writing-tools-for-agents) | Clear names, useful bounded responses and realistic evaluations improve tool ergonomics. Naming effects vary by model, so avoid universal performance claims. Retain namespaces; add paired success/denial scenarios. Do not rewrite third-party schemas to imitate vendor examples. |
| A02 — [Code execution with MCP](https://www.anthropic.com/engineering/code-execution-with-mcp) | Progressive discovery and filtering intermediate results in code can reduce context consumption. Secure execution adds operational cost. Stage code mode as a separate sandboxed service; keep each underlying action mediated by the gateway. |
| A03 — [Introducing advanced tool use](https://www.anthropic.com/engineering/advanced-tool-use) | Search, programmatic calls and examples address different tool-use bottlenecks. Its API features and measurements are vendor-specific. Stage authorized search and orchestration; do not change standard MCP discovery semantics or infer retry safety from model preferences. |
| A04 — [Effective context engineering for AI agents](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents) | Just-in-time retrieval and small useful context can outperform exhaustive loading. Exploration trades context for latency. Preserve bounded responses and selective permissions; stage task-based catalog views after measuring utility. |
| A05 — [Building effective agents](https://www.anthropic.com/research/building-effective-agents) | Simple composable workflows, environmental feedback and stopping conditions are useful foundations. The article notes that its tooling landscape has evolved. Keep agent delivery orchestration separate from the deterministic gateway data plane. |
| A06 — [Demystifying evals for AI agents](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents) | Graders, task outcomes, transcripts and environment state answer different questions. Model graders need calibration and can miss problems. Add deterministic state assertions; distinguish gateway checks from end-to-end model robustness evaluations. |
| A07 — [Effective harnesses for long-running agents](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents) | Explicit feature lists, incremental work and persistent progress help avoid premature completion claims. Evidence is from particular development harnesses. Use a traceable plan and validation record; retain unfinished features as staged work. |
| A08 — [Code Mode: the better way to use MCP](https://blog.cloudflare.com/code-mode/) | Uniform MCP connectivity can be presented as a code API in a restricted execution environment. Efficiency does not establish security equivalence. Defer code execution until sandbox isolation and per-action authorization can be demonstrated. |
| A09 — [How Cloudflare detects MCP traffic and helps secure it](https://blog.cloudflare.com/mcp-security-updates/) | Client, network and server controls see different parts of an action. URL paths alone do not identify MCP reliably. Retain protocol-aware checks; document that direct upstream access bypasses gateway policy unless network and upstream controls require mediation. |
| A10 — [Docker MCP Gateway: secure infrastructure for agentic AI](https://www.docker.com/blog/docker-mcp-gateway-secure-infrastructure-for-agentic-ai/) | Catalog curation, secret brokering, narrow tool views and interceptors are useful control points. Image signature verification is distinct from metadata review. Retain secret references; stage signed artifact admission rather than call hash pins supply-chain verification. |
| A11 — [MCP Security: risks, challenges, and mitigation](https://www.docker.com/blog/mcp-security-explained/) | Isolation, egress restrictions, curated artifacts and secret handling address distinct risks. Filtering cannot guarantee resistance to instruction/data ambiguity. Retain hardened deployment and add invocation constraints; no blanket “prompt firewall” claim. |
| A12 — [Jumping the line](https://blog.trailofbits.com/2025/04/21/jumping-the-line-how-mcp-servers-can-attack-you-before-you-ever-use-them/) | Tool descriptions can influence an agent before execution. The demonstrations concern particular historical clients. Add opt-in mandatory pinning during discovery as well as direct invocation; acknowledge trusted descriptions can still be malicious. |
| A13 — [Insecure credential storage plagues MCP](https://blog.trailofbits.com/2025/04/30/insecure-credential-storage-plagues-mcp/) | Plaintext configuration and conversation logs expose long-lived credentials. Specific client findings are historical. Keep secrets out of configuration documents, tool payloads and audit; a managed secret store remains an operator responsibility. |
| A14 — [Deceiving users with ANSI terminal codes in MCP](https://blog.trailofbits.com/2025/04/29/deceiving-users-with-ansi-terminal-codes-in-mcp/) | Display controls can make human review differ from model-visible text. The risk depends on renderer behavior. Add optional metadata-control rejection; preserve legitimate Unicode and avoid silently sanitizing the tool contract. |
| A15 — [Tool Poisoning Attacks](https://invariantlabs.ai/blog/mcp-security-notification-tool-poisoning-attacks) | Description poisoning, post-review changes and cross-server influence defeat simplistic approval assumptions. Pinning only detects changes to reviewed content. Add enrollment mode and maintain call-time contract checks; do not equate a pin with safe execution. |
| A16 — [Toxic flow analysis](https://invariantlabs.ai/blog/toxic-flow-analysis) | Combinations of access to sensitive data and exfiltration sinks create risks beyond individual tool labels. A gateway lacks complete provenance and intent. Add recipient/value constraints now; stage cross-tool information-flow enforcement. |
| A17 — [Timeouts, retries, and backoff with jitter](https://aws.amazon.com/builders-library/timeouts-retries-and-backoff-with-jitter/) | Retry amplification can worsen overload; side effects and recovery behavior require care. These are distributed-systems lessons, not MCP-specific prescriptions. Retain timeouts, bounded admission and no automatic side-effect retry. |
| A18 — [Making retries safe with idempotent APIs](https://d1.awsstatic.com/builderslibrary/pdfs/making-retries-safe-with-idempotent-apis-malcolm-featonby.pdf) | Caller request identifiers need parameter binding and defined response semantics, including late arrivals. A gateway cannot impose this contract on an arbitrary backend. Defer automatic retry/deduplication until upstream support exists. |
| A19 — [Secure a C# MCP Server with Auth0](https://auth0.com/blog/secure-csharp-mcp-server-with-auth0/) | Resource identity, audience validation, discovery and per-tool permissions must work together. Implementation examples are C# and Auth0 specific. Retain JWT resource checks and distinguish current service auth from a complete interactive delegated consent lifecycle. |
| A20 — [MCP Server Mediation](https://www.gravitee.io/blog/mcp-server-mediation-securing-third-party-mcp-connections) | Mediation should preserve caller accountability while brokering upstream credentials. This is vendor guidance, not an independently measured comparison. Retain tenant isolation/token exchange/audit and stage user-consent and credential-vault workflows. |

## Research papers (10)

| ID / paper and reviewed body areas | Finding, limitation and gateway decision |
|---|---|
| P01 — [Zanzibar: Google's Consistent, Global Authorization System](https://www.usenix.org/system/files/atc19-pang.pdf), USENIX ATC 2019. Data model, timestamp/config consistency, implementation and evaluation. | Relationship checks need explicit consistency semantics, especially when authorization and content change separately. Existing OpenFGA checks use pinned models and higher consistency; this does not reproduce Zanzibar's content-bound consistency tokens. Retain fail-closed checks and document that distinction. |
| P02 — [The Protection of Information in Computer Systems](https://web.mit.edu/Saltzer/www/publications/protection/Basic.html), Saltzer and Schroeder, 1975. Basic principles and [descriptor/capability mechanisms](https://web.mit.edu/Saltzer/www/publications/protection/Descriptors.html). | Fail-safe defaults, complete mediation, least privilege, simplicity and usable controls apply directly. The authors explicitly warn that design principles do not prove absence of flaws. Enforce constraints on every call and keep permissions understandable and bounded. |
| P03 — [Not what you've signed up for](https://arxiv.org/html/2302.12173v2), v2. Threat taxonomy, synthetic/real application setup, demonstrations and limitations. | Untrusted retrieved data can redirect model actions and influence responses. Demonstrations are not an exhaustive modern-model benchmark. Restrict concrete effects independently of prompt content; acknowledge text-only manipulation remains outside the gateway's control. |
| P04 — [InjecAgent](https://arxiv.org/html/2403.02691v2), v2. Benchmark construction, harm/exfiltration goals, metrics and limitations. | Test both direct harm and extraction followed by transmission. Its simplified interactions and fixed attack augmentation limit generalization. Use these attack categories in deterministic fixtures; do not claim to have run the InjecAgent benchmark or reproduced its attack rates. |
| P05 — [AgentDojo](https://arxiv.org/html/2406.13352v1), v1. Stateful environment construction, utility/security graders, evaluation and defense tradeoffs. | Evaluate actual task and attacker outcomes separately; filtering tools may also remove useful actions and fails when permitted tools suffice for an attack. Add paired permitted/forbidden argument scenarios with state assertions. This is an inspired regression suite, not AgentDojo certification. |
| P06 — [Identifying the Risks of LM Agents with an LM-Emulated Sandbox (ToolEmu)](https://arxiv.org/html/2309.15817v2), v2. Emulator requirements, evaluator validation and limitations. | Emulation accelerates finding unusual failure scenarios but can violate consistency or miss risks. Human validation in the paper is imperfect. Use emulation as a future test-generation aid, never as the release gate for whether an upstream effect happened. |
| P07 — [Defeating Prompt Injections by Design (CaMeL)](https://arxiv.org/html/2503.18813v1), v1. Threat model, explicit non-goals, control/data separation, policies, capabilities and evaluation discussion. | Trusted control flow and tracked data capabilities can enforce stronger boundaries than prompts. This requires an agent/interpreter architecture; ordinary gateway arguments have no reliable provenance. Add narrow destination constraints now; do not claim CaMeL's guarantees or protection from text-only attacks. |
| P08 — [Progent: Programmable Privilege Control for LLM Agents](https://arxiv.org/html/2504.11703v2), v2. Threat model, policy language/runtime and experimental setup. | Tool-specific argument conditions provide programmable least privilege. Policies can still permit harmful behavior within their allowed scope; text outputs are outside scope. Implement a smaller non-executable policy vocabulary. This is not a Progent implementation, and later-version solver/monotonicity claims are not imported. |
| P09 — [AgentSpec: Customizable Runtime Enforcement for Safe and Reliable LLM Agents](https://arxiv.org/html/2503.18666v3), v3. DSL, execution hooks, implementation, validity threats and future work. | Enforcement at action checkpoints is more testable than relying on a model to obey prose. Rules and generated predicates need review; discrete enforcement does not predict all future unsafe trajectories. Implement pre-invocation checks only, with no generated executable predicates or claimed trajectory guarantee. |
| P10 — [ReAct: Synergizing Reasoning and Acting in Language Models](https://arxiv.org/html/2210.03629v3), v3. Methods, ablations and interactive-task evaluation. | Alternating actions with observations supports adaptive problem solving. Task performance is not authorization evidence, and external observations may be adversarial. Preserve clear tool results; keep planner reasoning outside the authorization authority. |

## Decision boundaries

Implement this release: bounded argument policy, optional reviewed-only catalog, metadata display-control rejection, administration and state-based regressions. Preserve existing identity, OpenFGA, schema, tenant, traffic and deployment controls.

Stage with explicit prerequisites: durable independent human approval; interactive OAuth/consent; signed artifact admission; workflow provenance; authorized search; isolated code mode; idempotency-aware retry; independent model-based adversarial evaluation. Reject claims that a classifier, hash pin, prompt template or passing finite test suite establishes universal security. The plan lists acceptance gates and rollout risks for each category.
