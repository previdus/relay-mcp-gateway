01 / THE REQUEST PATH

What happens when an agent calls a tool?

Relay is a policy-enforcing MCP server in front of other MCP servers. The client authenticates to Relay, sees only the catalog its identity may access, then each tool call passes the authorization, route and destination checks before Relay forwards it.

StepWhat Relay doesWhy it matters
AuthenticateVerifies the configured service key, JWT/OAuth identity, or gateway-verified client certificate.Every later policy decision uses a verified identity.
DiscoverCollects bounded upstream definitions, applies visibility grants and publishes stable names or aliases.Hidden tools are not advertised to callers who cannot use them.
AuthorizeChecks identity grants and any configured role, tenant, relationship, argument, OPA or approval requirement.Discovery is not treated as permission to execute later.
RouteSelects only among configured, enabled, tenant-eligible targets, then checks the target contract and credential binding.Client input cannot choose an arbitrary host or rebind a physical tool name.
Forward & auditApplies deadlines, size and concurrency controls, forwards through the transport, and records metadata-only events.Operators can diagnose outcomes without storing tool arguments or results in audit events.
MCP clients still need a gateway service credential or a compatible identity provider. The AWS public demo credential is public by design and grants only the harmless echo tool.
02 / FIRST RUN

Run the local demo

Use a supported Node.js 22.14+ runtime. From the repository root, install the locked dependencies and start two sample upstreams with the gateway. The demo uses in-memory state and resets when stopped.

npm ci npm run demo

Open http://127.0.0.1:3000/admin/ and use the generated administrator key printed by the local process. Use the separate service key printed for MCP clients. Call tools/list to inspect the catalog; the sample exposes alpha__echo, beta__echo, and the stable alias echo.

{ "mcpServers": { "relay-local": { "url": "http://127.0.0.1:3000/mcp", "headers": { "Authorization": "Bearer <local-service-key>" } } } }
The demo uses loopback HTTP for local development. Do not copy that exception into an internet-facing deployment. Set TLS at a trusted ingress or terminate and verify mTLS in the gateway.

04 / MCP PROTOCOL

Protocol and catalog support

Relay uses the official MCP SDK for its server and supported upstream clients. Transport/version selection is negotiated or configured at the adapter. Optional protocol families are enabled explicitly and require separate identity permissions.

CapabilitySupportConfiguration / boundary
Streamable HTTPModern MCP and stateless legacy requests on the gateway endpoint.HTTPS is expected for remote service credentials; configure host/origin limits.
HTTP+SSELegacy upstream adapter.For enterprise credential bindings, pin explicit SSE request paths.
stdioTrusted process adapter with executable allowlisting and environment references.Do not allow arbitrary user-selected commands; process management is operator-controlled.
ToolsAggregated, namespaced, paginated, schema-validated discovery and calls.Permission-filtered at listing and checked again at invocation.
Prompts / resourcesOptional list/get, list/read, templates and completions.Feature flags plus separate grants; tool grants do not imply these permissions.
Notifications / callbacksModern notification and callback paths are opt-in; state can be shared with PostgreSQL.Legacy push callback bridging and some event variants remain open.
Tasks V2Opt-in tool task lifecycle with opaque caller-bound state.Independent-server interoperability and long-run retention/load need broader verification.

05 / IDENTITY

Choose how agents authenticate

Authentication selects one configured mode for the data plane. Do not mix modes hoping for fallback; unknown, invalid or ambiguous identities are denied. Admin access uses a separate administrator key.

ModeGood fitOperator setup and boundary
Service keysSmall trusted service fleets, local demos and controlled integrations.Use unique high-entropy credentials per identity; store hashes in state and keys in a deployment secret source. Rotate and restart all replicas together.
JWT / OAuth access tokensCentral workforce or workload identity providers.Pin issuer, audience, JWKS URL and resource. Optional scopes, token type/age rules, DPoP proof and jti revocation. The identity provider owns login and issuance.
Opaque-token introspectionProviders that issue non-JWT access tokens.Configure a trusted, bounded introspection endpoint and separate client credentials; outages fail closed.
Gateway-terminated mTLSWorkloads with certificate provisioning and renewal.Configure gateway certificate/key/client CA and map verified certificate thumbprints. TLS termination must occur in Relay; ingress-forwarded certificate headers are not trusted.
OAuth token exchangeUse a caller token to obtain a narrower upstream token.Bind inbound token exchange to the trusted token endpoint and bind issued token to its exact recipient. Provider-specific behavior needs compatibility testing.
The demo service token is intentionally public and limited to echo. Never place an admin key or customer upstream credential in an agent's client config.

Example: set up a JWT issuer

JWT_ISSUER=https://identity.example/tenant JWT_JWKS_URL=https://identity.example/tenant/keys JWT_AUDIENCE=relay-agents GATEWAY_RESOURCE_URL=https://gateway.example/mcp

Use JWT_ISSUER_PROFILES for multiple pinned issuer/audience/JWKS combinations and map each identity to its exact issuer. See authentication profiles and validation details ↗.

06 / PERMISSION MODEL

Authorize at the granularity your organization needs

Relay composes restrictions. A custom or external authorizer cannot grant beyond the identity's configured grants and deployment-owned safety boundaries.

Layer the checks

ControlWhat it restrictsWhen to use it
Tool allowlistExact public tool name or namespace wildcard per identity.Default least-privilege tool catalog.
Role grantsRequire one or more configured roles in addition to per-identity grants.Shared persona/department policy with distinct credentials.
Tenant scopeClient, upstream, route targets and relationship identifiers.Separate organizations, environments or customer accounts.
OpenFGARelationship-based tuples and model checks; optional pinned model and consistency setting.Resource ownership, team membership, delegated project access.
OPAExternal Rego decision composed as a required policy with local grants.Centrally operated policy decision point and reusable policy bundles.
Argument safeguardsBounded scalar, set, number and identity constraints before forwarding.Restrict account IDs, path choices, limits or caller-owned values.
Reviewed catalog pinsOnly approved definitions/fingerprints remain visible and callable.Block tool schema drift until review.
Human approval adapterSelected tools require an external permit bound to exact identity, args, route and revision.High-impact actions. Reviewer UI, identities and durable workflow remain external.
OpenFGA/OPA are optional adapters, not substitutes for provisioning their services securely. External policy outages fail closed. An approval response cannot undo an upstream action that already happened.

07 / ROUTING

Keep tool names stable; change the path safely

Routes publish an alias while the gateway owns the allowed target pool. Each target names a known upstream and physical tool. All strategies first remove targets that are disabled, tenant-ineligible or denied by route selectors.

StrategySelection behaviorExample use
stickyStable identity/tool bucket behavior.Keep an agent on a consistent backend.
weightedDistribute calls in proportion to target weights.Canary or traffic split. A failed call is not retried.
rendezvousWeighted deterministic hashing; adding a target moves only a portion of identities.Consistent affinity with controlled membership changes.
priorityPrefer highest-priority eligible targets; circuit state blocks an open target.Preference ordering without side-effect failover.
Custom selectorOptional remote plugin chooses only from an admin-configured candidate list.Organization-owned placement rules; candidate and identity projection stay constrained.

Example: a weighted canary alias

{ "routes": [{ "name": "search", "strategy": "weighted", "targets": [ { "upstreamId": "primary", "tool": "search", "weight": 9 }, { "upstreamId": "canary", "tool": "search", "weight": 1 } ] }] }

Tool contracts must be compatible across alias targets. Calls are not automatically replayed or moved after an ambiguous result, because tool side effects may already have occurred. See routing and catalog limits ↗.

08 / DESTINATION SECURITY

How Relay protects credentials from wrong endpoints

Configuration stores environment variable names, not secret values. A deployment-owned policy can pin each reference to an exact URL and purpose. In strict mode, bindings are required before the gateway reads a secret, and strict egress validates every DNS answer and connects to the checked address.

Basic credential reference

{ "upstreams": [{ "id": "docs", "url": "https://docs.example/mcp", "tokenEnv": "DOCS_MCP_TOKEN" }] } // DOCS_MCP_TOKEN is injected by the operator's secret manager. // Do not enter the token value in gateway.config.json.

Strict destination binding (deployment environment)

GATEWAY_REQUIRE_CREDENTIAL_BINDINGS=true GATEWAY_CREDENTIAL_BINDINGS=[{"reference":"MCP_UPSTREAM_DOCS","endpoint":"https://docs.example/mcp","purpose":"upstream-endpoint"},{"reference":"DOCS_MCP_TOKEN","endpoint":"https://docs.example/mcp","purpose":"upstream"}] GATEWAY_REQUIRE_EGRESS_VALIDATION=true
  • Exact scheme, hostname, port, path and purpose are matched; wildcards and redirects are rejected.
  • Every DNS answer is checked and the validated IP is used for the connection.
  • Cloud metadata and link-local ranges are denied; private subnets require narrow, explicit allowlists.
  • Built-in database, identity/policy, telemetry and gateway service calls can be guarded by strict egress.
This does not sandbox arbitrary in-process plugins, secure a compromised destination, or replace VPC security groups, Kubernetes NetworkPolicy, egress proxies and firewall rules. The project does not ship native AWS Secrets Manager, Azure Key Vault, Google Secret Manager or OCI Vault clients; use operator injection, workload identity/CSI, or a reviewed credential-provider adapter.

See enterprise destination controls ↗ for path-specific SSE bindings, OAuth exchange purposes, database TLS and plugin boundaries.

10 / EXTENSIBILITY

Replace a component without replacing the gateway

The runtime accepts typed contracts for authentication, authorization, routing, approvals, transport, credential resolution, storage, quotas and audit. A deployment plugin factory can assemble components for each published configuration.

createGateway(config, { authenticator, authorizer, router, approvalGate, transportFactory, credentials, limiter, audit });
Plugins are trusted application code, not uploaded scripts or sandboxed workloads. A timeout cannot stop every side effect. Run third-party or customer-authored extensions in separately identified services and restrict their network egress.

11 / ADMINISTRATION

Make configuration reviewable

The admin console organizes upstreams, service identities, routes, permissions, security controls and traffic settings. It supports draft editing, JSON editing, revision publishing, history/rollback, a route policy simulator, tool explorer and audit views.

  • Admin credentials are separate from agent credentials; keep the control plane on a restricted network.
  • Publish creates a versioned revision; requests keep the snapshot under which they began.
  • PostgreSQL shares configuration, audit, task state and distributed controls across replicas.
  • SQLite is intended for one local process; it is not multi-replica shared state.

The admin interface does not yet provide enterprise SSO, separation-of-duties approval for publishing, or a durable built-in human reviewer service. Put an authenticated admin ingress or identity-aware proxy in front of it.

12 / DEPLOYMENT GUIDES

Choose a runtime path

All deployments need a secure ingress, persistent/shared database for replicas, secret distribution, outbound network policy, backups and observability configuration. The sample manifests are starting points; adapt them to your organization's infrastructure and threat model.

Docker Compose

Compose is suited to a single host or a development environment. The included stack can run PostgreSQL and the gateway; configure TLS at a trusted reverse proxy and mount secrets read-only.

  1. Copy .env.example to a protected environment file and set separate admin and service credentials.
  2. Configure approved HTTPS upstreams, secret references, hosts, origins and permissions.
  3. Set DATABASE_URL to PostgreSQL for durable state. Back up and restore-test it.
  4. Start the stack and verify readiness, MCP discovery, access denial, logs and shutdown behavior.
docker compose up --build # validate the sample container separately npm run test:container

Review compose.yaml ↗ · Container and local notes ↗

Kubernetes and horizontally shared state

The sample manifest runs multiple gateway replicas with PostgreSQL shared state, bounded scaling, probes, a disruption budget, non-root execution, read-only root filesystem, dropped capabilities and service-account token automount disabled.

  1. Create namespace, TLS ingress, database, secret resources and an egress policy first.
  2. Provide identical key material and compatible secret versions to all gateway replicas.
  3. Set strict credential bindings and private CIDRs narrowly for required internal services.
  4. Set autoscaling/resources from load-test results, not sample values; configure multi-zone database backup and restore.
  5. Test readiness, pod replacement, permission changes, database outage/recovery and rollback with the target cluster.
kubectl apply -f deploy/kubernetes.yaml npm run test:kubernetes # Run acceptance only against a dedicated, disposable test context.
The Kubernetes acceptance evidence is from an isolated local cluster. It does not certify every managed Kubernetes service, ingress, cloud database or failure domain.

AWS public demo and production path

The checked-in CloudFormation stack deploys a CloudFront website and a one-instance App Runner gateway with an echo-only public tool. It generates an admin secret in Secrets Manager; the demo state is in memory and resets with instance replacement.

  1. Use a dedicated AWS account/profile with only the permissions listed in the AWS deployment guide.
  2. Confirm current App Runner, CloudFront, S3, ECR, logs and transfer charges. There is no hard spend cap.
  3. From PowerShell, authenticate the AWS CLI and Docker, then run ./deploy/aws/deploy.ps1.
  4. Test the MCP endpoint with the public demo token, which only grants echo. Retrieve the admin secret only from your AWS account.
  5. For production, replace in-memory state with managed PostgreSQL, add a private service boundary, TLS/custom domain, workload IAM role, secret delivery, network controls, backups and alarms.
$env:AWS_PROFILE = "your-profile" $env:AWS_REGION = "us-east-1" ./deploy/aws/deploy.ps1
This AWS template is a learning/demo stack, not a production multi-tenant reference architecture. Current source may contain work newer than the deployed demo image.

14 / READINESS & VALIDATION

What has been tested? What still needs evidence?

Repository records document unit, integration, browser, real PostgreSQL, container and isolated Kubernetes checks. Test results cover only the listed scenarios and software revision.

Before a production rollout

  • Run sustained load, large-pool routing and failure/chaos tests at representative concurrency.
  • Perform independent threat modeling and penetration testing; inspect egress and sensitive logs.
  • Validate your identity provider, ingress, managed database, secret manager and telemetry collector.
  • Set backup retention, restore drills, audit retention, key rotation, alerts and incident ownership.
  • Keep a tested rollback image and ensure older versions can read the published configuration schema.
Relay does not claim zero bugs, complete feature coverage of every optional MCP capability, universal cloud portability, or an independent security certification.
